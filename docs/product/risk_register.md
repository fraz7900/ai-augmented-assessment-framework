Likelihood/impact are qualitative (Low/Medium/High) — no incident data exists yet to quantify them, and presenting false-precision numbers would contradict this project's own stated documentation standard (see `PROJECT_CHARTER.md` Section 2's business problem framing).

| R-12 | Nothing outside `AssessmentService` currently prevents a direct-repository call from bypassing the finalized-assessment evidence lock — and the sanctioned path itself checked the status in a different transaction from the write | AI/data governance (found in Sprint 2 risk review) | Low for the bypass; the check-then-act window was live on every guarded write | Medium (would silently break the audit-immutability guarantee) | **Closed, Sprint 21 (prevention + tamper-evidence); one residual disclosed below** | Carried honestly from Sprint 2 to Sprint 20 without being closed. Sprint 21 closed the prevention half: `AssessmentRepository._assert_writable` re-reads the assessment's status *inside the transaction that performs the write*, on the five write methods `AssessmentService` already guards (`add_evidence_link`, `update_evidence_link_review`, `set_practice_finding`, `create_evidence_request`, `resolve_evidence_request`). `update_status` is deliberately excluded — it must be able to reach FINALIZED. Investigating the fix found a second, unrecorded defect this entry had never named: the service read the status through `get_assessment()` (one session, opened and closed) and then wrote through a *second* session, so an assessment finalized between those two moments was written to anyway — R-11's check-then-act bug class, on the audit-immutability path. Moving the read into the writing transaction closes it: on SQLite's default rollback journal (`journal_mode=delete`, verified, no WAL anywhere in the codebase) the shared lock taken by the read is held until the write commits, so a concurrent finalize cannot land in between. Ten tests in `repositories/tests/test_assessment_repository_finalization_guard.py` call each repository method directly against a finalized assessment — this entry's own sentence, made executable. Prevention alone is application code and does not survive someone editing `assessments.db` directly, so the detection half followed in the same sprint: `services/audit_seal.py` canonicalises the whole record — assessment, evidence links, practice findings, both append-only history trails, evidence requests — into one SHA-256 written at finalization, and `GET /assessments/{id}/verify` recomputes it and reports `verified` / `altered` / `unsealed` / `unverifiable` (four states, not a boolean: "no seal" and "seal does not match" are opposite situations). Twenty-two tests, including eight that open the SQLite file behind the application's back and edit a finalized record — an evidence link's practice reference, a deleted link, a rewritten status-history note — then assert detection. A per-row hash chain was considered and rejected as a second mechanism to keep correct on every write, for localisation nobody has asked for; one digest covers the finalized record completely. **Residual, disclosed:** a digest stored beside the record it protects proves nothing against someone who edits the record and recomputes the seal, so the seal is printed into every PDF/XLSX export and returned by finalize — the real tamper-evidence is a reader comparing an old report's printed seal against `/verify` today, which depends on someone having kept a copy. Assessments finalized before this existed carry no seal and are reported `unsealed`, never `verified`; they are deliberately not sealed retroactively, since a seal written now would attest only that the record has not changed since today.

| R-16 (new) | Retrieval-only mapping has a real, disclosed precision ceiling: domain-general cybersecurity vocabulary produces nontrivial similarity between genuinely unrelated practice/evidence pairs near the confidence threshold | AI quality (found in Sprint 5, ADR-0011) | High (observed live, not hypothetical) | Medium — mitigated by mandatory human review before any score impact, but still creates review burden | Open, mitigated by human-in-the-loop, not by model accuracy | Directly observed in the Sprint 5 live demo: `ASSET-1a` (an asset-inventory practice) proposed at confidence 0.71 against access-provisioning policy text — a real false positive from vocabulary overlap, not a hypothetical. Threshold (0.55) was empirically calibrated (correct pairs 0.65-0.78, incorrect pairs 0.43-0.53) but the gap is real, not large. `review_evidence` requires an explicit human decision before any proposal counts toward a score, which is why this is "mitigated," not "unmitigated" — a future generative verification layer (deferred) would reduce reviewer burden, not just catch a hard failure **Consulted and acted on, Sprint 23 (ADR-0065):** a tester asked for an "accept all with confidence > 0.85" bulk action, and this row is what refused it — 0.85 sits above the 0.65-0.78 band correct pairs were measured in, so the cutoff selects from a range nobody has characterised rather than from the safest links. Filters by domain, status and confidence band shipped instead; they change what a reviewer reads and never a record. The review burden this row names as the residual is therefore reduced but not removed, and the queue's real length is the precision finding in the pilot readiness audit rather than anything this row's threshold controls. **Quantified, Sprint 24 (ADR-0071):** the open question of whether 0.012 precision was a small-corpus artifact is answered — it is not. Across 5 to 505 documents precision moved 0.0117 to 0.0113, and the proposal count saturated at 355, which is every uncovered C2M2 practice. The engine proposes one candidate per practice, so the false-positive count is a property of the framework rather than of the evidence, and no amount of better or more evidence reduces it. Raising the threshold is not the fix either: this row's own calibration puts a confirmed false positive at 0.71, inside the 0.65-0.78 correct band. The review burden named above is therefore structural until candidate selection becomes competitive rather than absolute — a change with real recall consequences, deliberately not made in the sprint that measured it. |

## Review cadence

This register is updated at the end of every sprint as part of that sprint's consulting deliverables doc (see `docs/consulting/sprint-0X-deliverables.md`, Risk Assessment section) and reconciled back into this master file when a risk's status changes.
| R-33 (new) | OCR-recovered text is approximate, and the product's credibility rests on verbatim quotation: a citation drawn from an OCR'd page may not match the source page character-for-character, and nothing downstream of ingestion can tell the difference | AI quality / product (found in Sprint 19, ADR-0055) | High for any scanned document (OCR is approximate by nature, not by defect) | Medium — a misquoted citation in an audit deliverable is exactly the failure the chunker fix (140→2 mid-word chunks) was undertaken to prevent | Open, disclosed and narrowed | Disclosed at every layer rather than hidden: `ParseStatus.SUCCESS_OCR` is deliberately a *warning* tone in the upload UI, the message tells the uploader to check any passage against the source page before relying on it, and `parser_version` records the OCR engine so a citation's provenance is reproducible (ADR-0042). **Narrowed in Sprint 21** (ADR-0059): a part-scanned document now OCRs only the pages that lack a text layer and reports `SUCCESS_PARTIAL_OCR`, so a mostly-digital document no longer has every page treated as approximate — the reviewer is pointed at the specific pages that are. Not closable by better OCR: the residual is inherent to reading an image. |
| R-34 (new) | ADR-0057's scoring correction can lower a score that was already reported to a stakeholder, and the platform has no way to tell anyone holding the earlier number that it changed or why | Product / stakeholder communication (found in Sprint 20, ADR-0057) | Certain wherever a finding claimed credit without a linked evidence trail | Medium — a maturity level that drops between two readings, with no explanation attached, reads as the tool being unreliable rather than as the earlier number having been wrong | Open, disclosed | The intended effect, not a regression: the earlier number was the defect. No historical data was rewritten, and the finding and its rationale remain visible with the unsupported-credit status surfaced on the dashboard and in `finalization-readiness`. The gap is communication, not correctness — the same shape as R-21 (a stale export in circulation), and the same mitigation applies: exports carry a generation timestamp, and since ADR-0060 a finalized one carries a seal that identifies precisely which version of the record it came from. Revisit if this platform ever gains point-in-time or recurring reporting. |
| R-35 (table half closed Sprint 22) | Asynchronous ingestion holds every queued upload in memory until a worker frees up, and the `ingestionjob` table has no retention policy | Technical / operational (found in Sprint 21, ADR-0059) | Low (bounded by construction) | Low — worst case is `max_pending_ingestions × max_upload_bytes` (250MB at the defaults) of resident memory, on a machine that is already running local embedding and OCR | **Half closed, Sprint 22 (ADR-0064); the in-memory half stays open and disclosed** | Two separate problems were recorded in one row, and only one of them is now solved. **The table half is closed:** terminal jobs are deleted once their `finished_at` passes a configurable window (30 days by default, 0 to disable), swept at startup and after each job finishes. `QUEUED` and `RUNNING` rows are never swept however old they are, and a terminal row with no `finished_at` is kept rather than dated by a timestamp that means something else — deleting live work would erase an upload that afterwards is indistinguishable from one nobody submitted. ADR-0064 argues the 30 days from the horizon of the question a job row answers rather than picking a number, because the volume measurement ADR-0059 deferred to is not reachable on the deployment this charter scopes. **The in-memory half is unchanged and is the half with a cost:** the bound is deliberate — the synchronous endpoint had natural backpressure, accepting uploads immediately removes it, so `max_pending_ingestions` reintroduces it explicitly and returns 429 rather than queueing without limit. Disk spooling was considered and rejected twice, as trading a bounded memory commitment for an unbounded cleanup problem (orphaned spool files after a crash); it changes the queue's failure model rather than extending a retention sweep, so it stays a separate decision. |
| R-36 (new) | The finalization seal (ADR-0060) is stored in the same SQLite file it protects, so it detects tampering only when compared against a copy that left the database; and assessments finalized before it existed carry no seal at all | AI/data governance (found in Sprint 21, ADR-0060) | Medium — the mechanism works, but its evidentiary value depends on an operator having kept an export | Medium — an unqualified claim of "tamper-evident" would be stronger than what the design supports, which is the kind of overreach this project's own discipline forbids | Open, disclosed, mitigated by design not by assertion | Stated in `services/audit_seal.py`'s own module docstring rather than only here: a digest stored beside the record it protects proves nothing against someone who edits the record and recomputes the digest over it. Mitigated by making a copy leave the database as a matter of routine — every PDF and XLSX export prints the seal, and the finalize response returns it — so a reader holding an older report can check its printed value against `GET /assessments/{id}/verify`. That comparison is the actual tamper-evidence. Pre-ADR-0060 assessments report `unsealed`, never `verified`, and are deliberately not sealed retroactively: a seal written today would attest only that the record has not changed since today. An external timestamping notary was rejected as the first network call in the assessment path, against charter Section 7. |
| R-37 (new) | Audit-trail attribution (ADR-0061) trusts an `X-Remote-User` header set by the reverse proxy, so anything able to reach the backend directly can claim to be any user | Security / data governance (found in Sprint 21, ADR-0061) | Low in the deployed stack (the backend publishes no host port; nginx is the only route), certain for a direct API call in development | Medium — a forged actor in an audit record is worse than no actor, because it looks like evidence | Open, accepted, scoped to the deployment's existing perimeter | Attribution is exactly as strong as the perimeter the whole deployment already depends on, and no stronger; `core/identity.py` says so explicitly rather than implying more. The alternative — real authentication in the application — is "Won't (for MVP)" charter scope and would be a large security-sensitive surface for a single-user product. Two deliberate hedges limit the damage: a request with no identity records the sentinel `unauthenticated` rather than a plausible name, and pre-attribution rows keep NULL, so "nobody was authenticated" and "we did not record this at the time" stay distinguishable. The actor fields are covered by the seal (payload version 2), so a recorded actor cannot be quietly rewritten after finalization. Revisit when this platform gains an operator identity of its own — which would also allow signing seals rather than only hashing them (ADR-0060's Alternatives). |
| R-38 (new, mitigated same sprint) | No backup or restore procedure existed for the Docker volume holding every assessment, audit trail and seal, and the whole vector store — for a product whose central claim is an immutable audit record | Operational (found in Sprint 21 while auditing pilot readiness) | N/A — addressed | Critical if it had been hit: total, unrecoverable loss of every assessment the platform had produced | **Mitigated, Sprint 21; residual disclosed** | Found by looking for it, not by losing anything: nothing in `deployment/`, `docs/architecture/` or the README mentioned backup or restore. `scripts/backup.sh` now snapshots the volume to a timestamped tarball with a SHA-256 beside it, and `scripts/restore.sh` verifies that checksum, requires the volume name typed to confirm, and deliberately has no `--force` — it is the one operation in the repo that can destroy an audit record. The stack is stopped for the snapshot on purpose: SQLite can be copied consistently while live, LanceDB cannot, and a half-copied vector store restores into an assessment whose citations point at chunks that are not there. `backend/tests/test_deployment_config.py` asserts the scripts exist, stay executable, still name the volume the compose file declares, and remain documented — the same drift check that already guards the nginx upload ceiling. **Residual:** no schedule, no rotation, no off-machine copy. Those depend on where this is deployed, and a default invented here would be a guess dressed as policy. |
| R-39 (mitigated Sprint 22; residual as R-40) | Scoping documents to assessments (ADR-0062) narrows the evidence chooser but does not separate clients: the attach flow still browses every document on the instance, so one organisation's policy can be attached to another organisation's assessment deliberately | Product / data governance (found in Sprint 21, ADR-0062) | Low for the single-organisation deployment the charter scopes; certain if two clients are ever put on one instance | High in that scenario — evidence from one client appearing in another's assessment is a confidentiality failure, not merely a usability one | **Mitigated, Sprint 22 (ADR-0063); residual disclosed as R-40** | Closed as written by ADR-0063: an `Organization` owns assessments and documents, every list a person reads is scoped to one, and a cross-organisation attach is refused twice — in the service before any work is done, and again in the repository inside the transaction that performs the write, the same two-layer treatment ADR-0060 gave the audit-immutability guarantee. The scenario this row describes — a reviewer pulling one client's policy into another client's assessment through the product — is no longer reachable. What that required was reopening PROJECT_CHARTER.md Section 12's multi-tenancy exclusion for its data-model half only, by direct project-owner instruction, the same route Sprint 19 used for OCR. The part not closed is a different sentence, and is carried as R-40 rather than folded in here: separation enforced by the product is not separation enforced against a caller that bypasses it. |
| R-40 (new) | Client separation (ADR-0063) is enforced by the application, not by authentication: anything able to reach the API directly can pass any `organization_id` and read or write any organisation's data, and a document predating the registry (ADR-0039) carries no organisation for the boundary check to test | Security / data governance (found in Sprint 22, ADR-0063) | Low in the deployed stack (the backend publishes no host port; nginx is the only route), certain for a direct API call in development | Medium-High — separation that looks total and is not is more dangerous than separation known to be partial, because it invites exactly the two-client deployment it cannot defend | Open, disclosed, bounded by the deployment's existing perimeter | This is the same perimeter assumption R-37's attribution model already rests on, and the same reason the stack must not be exposed to a network — not a new exposure, but a new place where trusting the perimeter matters. Closing it needs authentication, which stays out of scope: Section 12 was reopened for the data model only. The 27-of-30 legacy documents with no registry row are allowed through the check rather than refused, because refusing them would break real assessments to enforce a boundary the data cannot express; the honest fix is a registry backfill, which is unstarted. Mitigation meanwhile is unchanged deployment discipline, plus the fact that the product itself can no longer cross the boundary. |
