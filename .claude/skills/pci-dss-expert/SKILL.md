# PCI DSS Expert

Grounding knowledge for working with the Payment Card Industry Data Security Standard (PCI DSS) v4.0.1 in this project. Load this skill before editing `framework_mapping/pci_dss_v4.yaml`, PCI-specific mapping logic, or any content that claims to represent PCI DSS structure.

## The defining constraints: copyright (like ISO 27001/SOC 2) AND a genuinely deeper structure (unlike anything else)

**PCI DSS v4.0.1 is copyrighted, all-rights-reserved content**, confirmed directly: the source PDF's own page 1 states "©2006 - 2024 PCI Security Standards Council, LLC. All Rights Reserved," and no public PCI SSC reproduction license was found (unlike CIS Controls' Creative Commons license, ADR-0025). This is true even though the document is freely downloadable at no cost — the same "free to download" vs. "licensed for reproduction" distinction ADR-0026 established for SOC 2. Given that, this framework gets the same **statement-only** treatment as ISO 27001/SOC 2, not CIS Controls' full-transcription treatment — this applies at whatever granularity is transcribed (see below): only the bolded requirement statement itself is ever real text, never the surrounding Testing Procedures/Purpose/Good Practice/Definitions/Customized Approach Objective/Applicability Notes elaboration.

**PCI DSS also has a real structural difference from every other framework in this project: it is THREE levels deep**, not two. A top-level Requirement (e.g. "Requirement 1: Install and Maintain Network Security Controls") breaks into Sections (e.g. "1.1 Processes and mechanisms for installing and maintaining network security controls are defined and understood."), which in turn break into individual numbered "Defined Approach Requirements" (e.g. 1.1.1, 1.1.2, 1.2.1-1.2.8...) — **249 of these leaf items, directly counted**, exist across all 12 Requirements (ADR-0027's original ~205 estimate, and a later ~250 guess made mid-transcription, were both rough approximations superseded by this real count).

**As of ADR-0029 (Sprint 16), this project transcribes at the full leaf level (N.N.N)**, extending ADR-0027's original Section-level (N.N) transcription. This was always named as real, disclosed future work in ADR-0027, not a rejected idea — it was picked back up when a prior session's in-progress extension was found uncommitted and finished. The Section level didn't disappear: each Section is now modeled as the enclosing `Objective`'s title (see below), not as a `Practice` in its own right.

**Every consumer of `framework_mapping/pci_dss_v4.yaml` must respect this**: `Practice.text` is the real, verified **leaf-level Defined Approach Requirement statement** (e.g. `"9.2.1 Appropriate facility entry controls are in place to restrict physical access to systems in the CDE."`), never the Testing Procedures/Purpose/Good Practice/Definitions/Customized Approach Objective/Applicability Notes elaboration that accompanies it in the source. `FrameworkDefinition.scoring_note` states this explicitly.

## Model structure

- **12 Requirements, 63 Sections, 249 Defined Approach Requirements** (Sections: 5+3+7+2+4+5+3+6+5+7+6+10 across Requirements 1-12: Install and Maintain Network Security Controls; Apply Secure Configurations; Protect Stored Account Data; Protect Cardholder Data with Strong Cryptography During Transmission; Protect Against Malicious Software; Develop and Maintain Secure Systems and Software; Restrict Access by Business Need to Know; Identify Users and Authenticate Access; Restrict Physical Access; Log and Monitor All Access; Test Security Regularly; Support Information Security with Organizational Policies). Modeled as one `Domain` per Requirement (short_code `"REQ-01"`-`"REQ-12"`, zero-padded), **one `Objective` per Section** (title carries the Section's own real number and statement, e.g. `"3.5 Primary account number (PAN) is secured wherever it is stored."` — mirroring how NERC CIP's own Objectives carry a real requirement number and title rather than a placeholder), and **one `Practice` per Defined Approach Requirement** under that Objective.
- `scoring_model` is `"coverage"` (mirrors every non-C2M2 framework here) — PCI DSS has no native maturity-level concept. `Practice.mil` is always `None`.
- `Practice.applicability` is always empty — no per-leaf-item applicability-scope concept was verified in the source (PCI DSS does have SAQ-type engagement scoping, but it doesn't map cleanly to a per-item field the way NERC CIP's impact tiers, CIS Controls' Implementation Groups, or SOC 2's Common/Additional-category distinction do — don't fabricate one).
- All 12 Requirements are fully populated (`practices_populated: True` throughout) — this is **not** a partial-transcription state like NERC CIP's original stub start (ADR-0021). Every Section and every leaf item's ID and statement is real and complete.

## Verification method (confirmed, don't re-litigate)

- ADR-0027 (Section level): fetched the real "Payment Card Industry Data Security Standard: Requirements and Testing Procedures, v4.0.1" PDF (June 2024 — the current active version; v4.0 was retired 31 December 2024) from a third-party institutional mirror, verified via `pypdf` to be genuine PCI SSC content (real title page, the exact copyright notice quoted above, 397 real pages) before extracting anything from it, the same "verify the actual content, don't trust the URL" discipline ADR-0025/ADR-0026 established. The 63-Section total was confirmed two independent ways: an automated grep-based count of the document's own N.N-pattern numbering, and a manual read of each Requirement's own real "Sections" summary block.
- ADR-0029 (leaf level): re-fetched and re-verified the same PDF the same way. Leaf statements were extracted programmatically from the PDF's own "Defined Approach Requirements" column (never the adjacent Testing Procedures/Purpose/Good Practice/Definitions/Customized Approach Objective/Applicability Notes columns), then every Requirement's raw extracted text was read by hand against the generated candidates to catch extraction artifacts — six real issues were found and corrected this way (a table layout that merged a short requirement and its testing procedure onto one text line for a few short leaf items, and five leaf statements where the PDF's own reading order put a cross-referenced requirement number at a position an extraction heuristic expected a new leaf item to begin, truncating the sentence). 249 was confirmed by direct count during this transcription, cross-checked against the document's own N.N.N-pattern numbering.

## Rules for this project

1. **Never present a Testing Procedure, Purpose, Good Practice, Definition, Customized Approach Objective, or Applicability Note as if it were the requirement itself.** Any UI, report, or documentation surface showing PCI DSS data must make clear that only the bolded Defined Approach Requirement statement is verified/available.
2. **Never hardcode PCI DSS structure in Python.** It belongs in `framework_mapping/pci_dss_v4.yaml`, generated by `backend/scripts/generate_pci_dss_yaml.py`, per ADR-0002.
3. **Do not attempt to fill in Testing Procedure/Purpose/Good Practice/Definitions/Customized Approach Objective/Applicability Notes text from memory, ever**, even if you are confident you know it — the same discipline ADR-0024/ADR-0026 established for ISO 27001/SOC 2's excluded text, and the same discipline that applied to the (now-transcribed) leaf-level requirement statements themselves before ADR-0029.
4. **Cross-framework equivalence involving PCI DSS is methodologically weaker than the C2M2/NIST/CIS Controls pairings** (see `framework_mapping/cross_framework_equivalence.yaml`'s own header and ADR-0027/ADR-0029) — these are leaf-statement judgments, not the full-text-vs-full-text semantic comparison those pairings use. Treat it with the same caution as the ISO 27001/SOC 2 pairings.
5. **Watch for "account" vocabulary collisions during any future equivalence review.** PCI DSS's "account data" almost always means payment card account data (PAN, cardholder data), while most other frameworks' "account" language means user/system accounts — the embedding will surface superficially plausible matches across this distinction that a careless reviewer could accept incorrectly. Always check what "account" means in context before accepting a candidate.
6. **PCI DSS has no dedicated business-continuity/disaster-recovery Section**, unlike SOC 2's A1.1-A1.3 or CIS Controls' Control 11 — a real, confirmed gap (PCI DSS's scope is protecting cardholder data via security controls, not business continuity). Don't force a match for a NERC CIP recovery-plan part against an unrelated PCI Section just because a superficial keyword overlaps.
7. **Every PCI DSS Requirement opens with an "N.1" Section whose only two leaves are purely administrative** ("policies and procedures documented, kept up to date, in use, known" / "roles and responsibilities documented, assigned, understood") — neither ever states the substantive technical requirement the Section-level statement (e.g. "Processes and mechanisms for X are defined and understood") implies. A NERC CIP (or future framework) part that reads as a real match against that Section-level statement will often NOT have a genuine leaf-level match under it — ADR-0029's re-review dropped nine NERC CIP equivalence entries for exactly this reason. Check the actual leaf text before accepting a match to an "N.1" Section.
8. **When adding a new framework in the future, check for practice-ID collisions with existing frameworks before assuming the loader will handle it correctly.** This project found and fixed a real bug during PCI DSS's addition: `services/framework_loader.py`'s practice-text index used to be keyed by bare `practice_id` alone, so CIS Controls' Safeguard "5.1" and PCI DSS's Section "5.1" (an identical bare ID string, back when PCI DSS's Practice ids were Section-level) silently collided. Fixed by keying the index by `(framework_name, practice_id)`. Any future framework whose ID scheme could plausibly collide with an existing one (short numeric-dotted forms are the highest risk) should be spot-checked against this exact failure mode after loading.

## Example usage

Extending PCI DSS equivalence to a new framework, or reviewing NERC CIP↔PCI DSS more thoroughly: load this skill first to confirm which leaf items exist under a given Section before making any claim about "what PCI DSS requires" — the honest answer for any specific mechanism not covered by a real leaf statement is "not part of the verified text in this project's data," not a guess filled in from general PCI DSS familiarity, and not an assumption that the Section-level summary statement alone establishes the mechanism.
